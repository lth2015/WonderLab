## 所有者最新授权的工作方式

本轮由 Claude Code 主导具体工程推进，可以给 Codex 分配任务。Codex 继续世界观、生灵、故事与创作衔接，并承接明确的素材或其他交接。日常取舍由双方直接商量，不因普通问题打断所有者休息。

这项分工不把所有世界设定都变成当下必须实现的功能。具体展开顺序由 Claude 结合现有场景安排；Codex 为需要深入的地方补充创作资产。

## 两个入口

| 用途 | 位置 | 写法 |
|---|---|---|
| 认领、提问、建议、协调、交付通知 | collab 分支的 mailbox/ | 每条消息新增一个文件，只新增，不改删别人的文件 |
| 出图、素材、一件明确的工作 | 任务所在分支的 docs/handoff/ | 一事一文件，在原文件记录需求、接收、问题、结果与验收 |

collab 分支永远不合并到 main，不在其中提交产品代码或世界观正文。消息可以指向其他分支的文件与提交。

消息文件名用 UTC：YYYY-MM-DD-HHMM-发件人-收件人-主题.md。前三行依次写“状态：”“涉及：”“回复：”；按主线约定填写。

## 每次开工时

先拉取 collab，查看写给自己的新消息；再看已知任务分支的最新交接文件。改代码前先认领明确的分支与文件范围，避免覆盖对方正在做的事。

素材开始生成前再次检查状态。任务已经完成或撤回时，按最新消息结束，避免重复消耗与重复交付。

具体工作完成后，在原任务文件写明文件路径、提交号、实际检查与尚存问题，并在信箱通知对方。交付与验收分别记录。

## 分支与工作现场

Codex 使用 codex/*，Claude 使用 main-emzgyk-*。不 force-push，不删除别人的分支，保留双方未完成的工作。

一般不修改对方的工作分支；只有交接明确指定的素材或回执提交，才在约定范围内处理。具体例外若有歧义，先在信箱与主导方确认。

推送信箱前按主线约定同步 collab；并行出现新消息时，只重放自己尚未推送的新增消息，不覆盖对方。

世界观正文继续在 codex/wonderful-world-values 的 value/ 下维护。当前创作入口是 [两条创作线，在湖边相接](../10-creative-confluence.md)和 [从一湾水，长成一方天地](../11-paths-from-the-lake.md)。

## 验证与实际能力

图像文件存在、透明通道存在、静态图看起来合适，与进入场景后表现合适，是不同的检查。双方在消息里只报告自己实际做过的部分。

本侧可用会话提供的图像生成与编辑工具，能做文稿、代码分析、构建、测试与功能请求检查。本机、手机和最终艺术验收不能因“桌面上有窗口”就视为已经具备。

Git 推送通道已经验证；本侧 GitHub PR API 的限制不阻止通过信箱交换成果。当前部署、合并与需要代办的 PR，由 Claude 按既有流程统筹。

## 会话停止后的限制

双方活跃时可以主动拉取信箱并执行任务；没有证据表明停止的会话能自动被另一方唤醒。不能把“准备回信”写成“对方已经收到”，也不能把仍未启用的通知机制写成已运行。

此前探索的 Git 信箱与桌面钩子原型没有安装、没有推送，已移到工作目录外保留。现在统一使用双方实际建立的 collab/mailbox/ 与 docs/handoff/，不另设第三套通道。
