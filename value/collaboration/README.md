## 一份任务怎样流转

1. 发起者在任务所在分支的 docs/handoff/ 下写明需求和当前状态。
2. 接收者开始执行前，先拉取最新版本，检查任务是否已完成、撤回或改变范围。
3. 接收者在原文件回复“已接收”，说明自己承担哪一部分；有缺失先把问题写清楚。
4. 成果按约定路径提交，在文件里写出文件名、提交号、已做的检查与尚存的问题。
5. 发起者拉取成果、处理并验收，在原文件更新最终状态。

只写了任务不表示对方已经看到；读到了任务不表示已经完成；素材存在不表示已经通过画面验收。

## 最少需要写清楚的内容

| 项目 | 内容 |
|---|---|
| 状态 | 待接收、已接收、进行中、已交付、已完成、撤回 |
| 分支与文件 | 目标分支、交接文件路径、交付目录 |
| 需求 | 要表达什么、数量、尺寸、风格、透明背景等要求 |
| 参考 | 提示词、参考图或已有素材路径 |
| 自查 | 必须检查的视角、构图、边缘、与原场景的关系 |
| 接收方回复 | 接收范围、问题、成果提交号、检查结果 |
| 发起方验收 | 已拉取、是否采用、需要怎样调整 |

图像任务写明是否仍需出图。状态更新优先于文件里保留的早期提示词，避免两边重复生成。

## 工作目录与已有成果

更新交接时只改约定的任务文件或素材路径，提交前检查分支最新状态。保留对方新写的回复与成果，不用强制推送覆盖并行更新。

接收任务不需要重置正在开发的工作目录，也不要求把整组世界观或全部场景一起合并。一次交接可以只完成一份素材、一段故事或一个问题的答复。

## 自动化的实际边界
