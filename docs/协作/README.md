> 2026-10-29 建立，同日按 Codex 的回信修订。所有者希望 Claude 和 Codex 长期协作、各自发挥长处，**以 Claude 为主统筹、可以给 Codex 分配工作**；两边有事直接商量，不必事事询问所有者。两边的入口文件 `CLAUDE.md`、`AGENTS.md` 都指向这里。

> **两边都运行在各自独立的云端会话里**：所有者桌面上看到的只是窗口，两边都碰不到所有者的电脑、账号和手机，只通过这个共享仓库交换成果。真机验收由所有者来做。

## 信箱：`collab` 分支

- 消息放在分支 **`collab`** 的 `mailbox/` 目录。这个分支只放消息，**永远不合并**进 main，也不放产品代码。
- **一条消息一个新文件**，文件名：`YYYY-MM-DD-HHMM-发件人-收件人-主题.md`，例如 `2026-10-29-1600-claude-codex-你好.md`。时间用 UTC。
- **只新增文件，不改、不删别人的文件**，所以两边各自推送不会冲突。推送前先 `git pull --rebase origin collab`（只 rebase 自己尚未推送的提交），**绝不 force-push**。
- 消息开头写三行：`状态：提议 / 认领 / 进行中 / 完成 / 求助`、`涉及：分支或文件`、`回复：所回复的文件名（没有就写无）`。
- 每次开始工作前，先 `git fetch origin collab` 看一眼 `mailbox/` 里有没有给自己的新消息。

## 做事的规矩

1. **先认领，再动手**：要改某块代码，先在信箱里发一条「认领」，写明分支和文件，避免两边同时改同一处。对方发过「认领」的地方，等对方「完成」再动。
2. **分支**：Claude 用 `main-emzgyk-*`，Codex 用 `codex/*`。一般不改对方的分支，不 force-push，不删别人的分支。**例外**：所有者或交接文件明确允许时，可以在对方分支的指定目录提交素材或回执；这时保留对方的并行更新，不改对方的产品代码。
3. **上线流程**（验证路线图 §2，不设冻结）：开分支 → PR、CI 通过 → 部署这个分支到 want.world 验收 → 合并到 main → 所有者打 `poc-r1.N` 标签。目前由 Claude 负责部署和合并；Codex 的 PR 也可以交给 Claude 部署验收后合并。
   **部署前先把最新 `origin/main` 合入待部署分支，再对合入后的提交完成 CI 与验收。** 部署会套用该分支的 `deploy/k8s`；旧分支曾覆盖 `gift.want.world` 的路由，不能只凭自己的场景代码可用就直接部署旧配置。
4. **交接东西**：具体的活（出图、素材、一段文稿）用交接文件：放在 `collab` 分支的 `docs/handoff/`，一事一文件，写明状态（待接收、已接收、进行中、已交付、已完成、撤回）、目标分支、交付路径、要求和自查项，接收方在同一文件末尾回复，发起方验收后更新最终状态。图片等成果放进交接文件指定的目录，原始素材不进 main。发出交接后，在信箱留一封短信指向它。
5. **状态分开记**：消息发出、已读、已交付、已验收是四件事，分别记录。执行前以最新状态为准：旧需求后来有「完成」或「撤回」的，按最新的办。
6. **不进仓库的**：`.env`、任何 key 或令牌、用户的笔画和句子数据（`strokes/` 只有 README）。key 不出现在消息、提交和聊天里。
7. **商量着来**：日常取舍有分歧，各自把理由写进信箱直接商量，由 Claude 统筹定下；真正需要所有者拍板的（产品方向、花钱、对外发布），攒起来等所有者来定，不为普通问题打扰所有者。不在对方的工作上直接覆盖。
