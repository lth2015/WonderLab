# 验证路线图（2026-10-26 起，约 6 周）

> 先冻结，再验证，最后决定商业化，而不是不断增加功能。
>
> 我们要验证的不只是「用户会不会玩」，而是：当没有积分、没有任务、没有排行榜，也没有任何人催促的时候，一个人是否还愿意回到自己创造的世界。

状态：已批准（2026-10-25）。产品决策见 [02 §11](02-product-design.md)。

## 1. 四个人群

隔离的是**实验之间的影响**，不只是人员。

| 人群 | 参加 | 不参加 |
|---|---|---|
| **A 同事**（3–5 人） | 笔迹采集（[strokes/README.md](../strokes/README.md)）、真机验收 | 所有用户实验 |
| **B 主持测试者**（8 人，手机、桌面各 4） | 主持测试 R1 | 日记式测试 |
| **C 日记测试者**（3–5 人，首次接触） | 一周日记式测试，最后访谈含实物意愿 | 主持测试 |
| **D 收鱼人**（约 5 人，**首次接触**） | 收到一条鱼 | 其他所有 |

- A、B、C 互不重叠。D 必须是从没见过产品的人。
- D 收到的鱼来自 B 或 C，这是实验设计的一部分，不算污染。但 **B、C 只能在完成自己的实验（含最终访谈）之后才能送鱼**，送鱼不得影响日记式测试的数据。
- **送鱼人只发链接，不讲解玩法，不指导怎么画。** 朋友之间正常的情感交流不用禁止，但要记录是否发生过指导（问送鱼人，也问收鱼人），有指导的样本单独标注。
- 招募筛选沿用 [testkit/招募.md](testkit/招募.md)：见过或听说过产品的人不进 B、C、D。

## 2. 版本与冻结

| 版本 | 内容 | 用于 |
|---|---|---|
| `poc-r1` | 10/30 冻结时的基础 PoC，**没有送鱼** | B 组主持测试、C 组日记式测试 |
| `poc-gift-r1` | `poc-r1` 加上送一条鱼 | 送鱼实验（B/C 送出、D 接收） |

- **冻结的是 R1 测试版本的功能和交互行为**，不是整个项目停止开发。10/30 是目标日期，打上 `poc-r1` 标签。
- 冻结后，R1 只接受影响测试、安全或稳定性的修复；新功能在其他分支继续开发，不进入 R1。
- **R1 的「一句成境」只用本地规则，不开 AI，也不设 AI 对照组**（2026-10-25 决定）。实验构建在打包时就固定为本地规则（`sceneMode: local`，带邀请令牌也不会请求 `/api/scene`），而不是靠运行时失败后退回；`world_ready` 记录这一模式，`npm run analyze` 发现测试者之间模式不同、或有句子经 AI 理解时会警告。R1 期间不根据反馈扩充关键词、不调整规则，阻塞性缺陷除外，且按附录记录版本变化。
- 每次修复记录：提交号、影响范围、测试结果（[附录](#附录冻结后修复记录)）。
- 如果某个修复改变了 H1/H2/H3 所测的核心体验，必须标记为新的实验版本，**数据不能直接合并**。
- 每条记录都带着**记录它的那个构建**（构建时写入的提交号、实验编号、日志格式版本），按事件、按回访分别标记，而不是导出时统一打上当前版本：测试期间网站更新过，旧记录仍然标着旧版本，导出文件列出所有版本（`builds`、`mixedBuilds`）。`npm run analyze` 发现版本混杂（包括同一份记录内部混杂）或不是冻结构建时会警告。没有版本标记的旧记录标为 `unknown`，不会被算到任何版本头上。
- 送鱼数据和基础 R1 数据分开分析，不混在一起。

## 4. 判定规则（测试开始前写定）

样本很小，百分比不是统计结论。保留明确的 Go / No-Go 机制，同时避免过早否定有潜力的方向。

### 4.1 主持测试（B 组，以 8 名有效测试者计）

| 假设 | 门槛 | 未达标后的行动 |
|---|---|---|
| H1 首次创造（5 秒内无求助落笔） | 8 人中 **≥ 7 人** | 优先排查首屏、触控响应与提示；修复后用新人复测 |
| H2 自主创造（自由段 ≥ 3 次无提示创造） | 8 人中 **≥ 5 人** | **暂停商业功能开发**，研究核心循环和世界深度；**继续**商业价值访谈（是否珍惜已有作品、是否愿意做成实物），以区分问题出在创造过程还是作品价值 |
| H3 主动保存或分享 | 8 人中 **≥ 3 人** | **不启动真实收费实验**，继续调查作品的情感价值；但**允许少量研究性实物打样**，看用户见到实体作品后是否改变看法 |

- 有效人数少于 8 时按原比例（H1 80%、H2 60%、H3 30%）向上取整，报告里会写明「N 人中需 M 人」。
- **无效样本**（中途离开、设备故障、事后发现见过产品等）由观察员在读结果之前写下原因（`notes.json` 的 `invalid` 字段）；它们保留在报告里，但不计入判定。原始日志全部保留。
- 「不确定」：未知（缺观察证据、没有自由段）多到足以改变结论时判为不确定，按 [testkit/测量有效性审查.md](testkit/测量有效性审查.md) 的口径处理，不为凑结论补录。
- H3 只衡量主动保存或询问分享，不是付费意愿指标；它决定的是能否启动**收费**实验，不否定实物方向本身。
- 文字理解不参与 H1–H3 的计算，但文字回应不如预期可能让人不再创造或不想保存。判定规则不变；分析时用观察记录里「文字回应是否成为停手或不想保存的原因」区分画的体验问题和文字回应问题（[主持人手册](testkit/主持人手册.md) §6、[验证报告模板](testkit/验证报告模板.md)）。关键词命中率只是诊断指标，不代表用户感受到的理解质量。

### 4.2 日记式测试（C 组）

| 门槛 | 未达标后的行动 |
|---|---|
| 5 人中 **≥ 2 人**一周内自发回来至少 2 次 | 判断是缺少陪伴价值，还是存在使用场景、设备或入口障碍（比如找不到入口、没加到主屏幕） |

### 4.3 送鱼实验（D 组）

不设单一门槛，记录一条漏斗，分析每个环节在哪里流失：

| 环节 | 记录 |
|---|---|
| 打开 | 收到链接后是否打开（问送鱼人和收鱼人） |
| 收下 | 鱼游到湖边后是否轻触水面收下（`gift_accepted`） |
| 理解 | 访谈：是否明白这是朋友亲手画的鱼 |
| 创造 | 收下后是否画出自己的第一条鱼（`npm run analyze` 的「收到一条鱼之后」） |
| 转送 | 是否主动把自己的鱼再送给别人（`gift_sent`） |

大多数人**没收下**时，先怀疑交互（没看懂「轻触水面」），不要急着判断概念失败。

### 4.4 实物（02 §14）

- H3 达标：允许进入实物需求验证和小批量打样。
- H3 未达标：不启动收费实验；允许少量研究样品。
- 只有在用户表达明确兴趣、供应链成本可接受时，才考虑真实收费实验。

## 5. 测试记录：只在本机，由参与者自己选择导出

- 主持测试：主持人用隐藏面板导出（`?mod`，左上角快速点 5 下），和以前一样。
- 日记式测试、送鱼实验：参与者在自己的手机上使用，记录跨天保存在本机，**由参与者自己决定是否导出**。测试说明里给一个链接（站点地址加 `/?study`），打开后看到：记录了什么、没记录什么、各项计数；可以填写匿名编号（如 P01）后导出，也可以不导出，或删除全部记录。说明文字见 [testkit/送鱼实验说明.md](testkit/送鱼实验说明.md)、[testkit/日记式测试.md](testkit/日记式测试.md)。
- 记录只有时间、次数和事件类型。**没有画的内容、写的字、姓名、手机号或链接。**参与者编号只接受字母、数字和短横线。
- 这一点由存储入口保证，而不是靠每个调用方自觉：每种事件只能保存登记过的字段（`src/lib/study-log.ts` 的 `STUDY_FIELDS`），字符串只能是简短的代号（字母、数字和 `- _ .`），其他字段一律丢弃；读出旧记录时再过滤一遍。新增事件类型不登记就编译不过，新增字段不登记就不会被保存。主持人的内存日志用同一份清单。
- 没有任何自动上传。
