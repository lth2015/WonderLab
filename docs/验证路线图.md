# 验证路线图（2026-10-26 起，约 6 周）

> 先收敛，再验证，最后决定商业化，而不是不断增加功能。（2026-10-29 起不设冻结，见 §2）
>
> 我们要验证的不只是「用户会不会玩」，而是：当没有积分、没有任务、没有排行榜，也没有任何人催促的时候，一个人是否还愿意回到自己创造的世界。

状态：已批准（2026-10-25）。产品决策见 [02 §11](02-product-design.md)。

## 1. 四个人群

隔离的是**实验之间的影响**，不只是人员。

| 人群 | 参加 | 不参加 |
|---|---|---|
| **A 同事**（3–5 人） | 笔迹采集（[strokes/README.md](../strokes/README.md)）、真机验收 | 所有用户实验 |
| **B 主持测试者**（8 人，手机、桌面各 4） | 主持测试 R1 | 日记式测试 |
| **C 日记测试者**（3–5 人，首次接触） | 一周日记式测试，最后访谈含实物意愿 | 主持测试 |
| **D 收鱼人**（约 5 人，**首次接触**） | 收到一条鱼 | 其他所有 |

- A、B、C 互不重叠。D 必须是从没见过产品的人。
- D 收到的鱼来自 B 或 C，这是实验设计的一部分，不算污染。但 **B、C 只能在完成自己的实验（含最终访谈）之后才能送鱼**，送鱼不得影响日记式测试的数据。
- **送鱼人只发链接，不讲解玩法，不指导怎么画。** 朋友之间正常的情感交流不用禁止，但要记录是否发生过指导（问送鱼人，也问收鱼人），有指导的样本单独标注。
- 招募筛选沿用 [testkit/招募.md](testkit/招募.md)：见过或听说过产品的人不进 B、C、D。

## 2. 版本与发布

| 版本 | 内容 | 用于 |
|---|---|---|
| `poc-r1` | 基础 PoC，**没有送鱼**；每个验收通过的版本打一个 `poc-r1.N` 标签 | B 组主持测试、C 组日记式测试 |
| `poc-gift-r1` | `poc-r1` 加上送一条鱼 | 送鱼实验（B/C 送出、D 接收） |

- **不设冻结**（2026-10-29 所有者决定，取代原定的 10/30 冻结）：R1 这一轮内继续开发，在这一轮内收敛。每项改动的流程：
  1. **开分支**，提 PR，CI 通过。
  2. **上线验收**：把这个分支部署到 want.world（在 Actions 里对该分支手动运行 Artifact Build，再用它的提交号手动运行 Deploy QA），所有者在线上验收。
  3. **验收后合并到 main**（合并会自动再部署一次 main）。
  4. **打标签**：在合并后的 main 上打 `poc-r1.N`（N 从 1 递增），在附录「发布记录」写一行。
- 测试者用的是当时线上的版本；每条记录本来就带着构建的提交号（见下文），不同版本的数据按版本拆开看。改动如果改变了 H1/H2/H3 所测的核心体验，在发布记录里标明，数据不能直接合并。
- **R1 统一在有声条件下测**（2026-10-26 决定）：iPhone 拨到静音时网页声音会完全消失且没有提示（YUHA 实测），产品不绕过静音键（02 待决问题），所以由测试准备来统一：主持人的设备和测试者自己的手机都在开始前把静音键拨到响铃、音量中等（[主持人手册](testkit/主持人手册.md) §2）。全程无声的样本单独标注，不剔除。
- **「一句成境」的三个数据集**（2026-10-25 决定），各有用途，不能混用：

  | 数据集 | 来源 | 用途 | 能不能据此改规则 |
  |---|---|---|---|
  | 固定测试集 | 主持人手册里的 10 句，原文锁定（含本地规则接不住的「天快黑了」「一个人的晚上」） | 让所有测试者面对相同输入；记录规则命中和实际回应 | **不能**，不为它们调规则，也不替换失败句 |
  | 规则校准集 | A 组同事自然写出的 15–50 句（[strokes/README.md](../strokes/README.md)） | 发现通用的表达缺口 | **能**，按下面四个条件 |
  | 真实验证集 | B 组测试者自己写的句子，以及他们对回应的主观评价 | 验证 | **不能**，R1 期间不改；留到 R2 |

  校准集用来改了规则，就不再是留出集：它说明的是规则对见过的说法适配得如何，不是泛化能力。真正的验证只看真实验证集。
- **修改规则的四个条件**，缺一不可：
  1. **通用**：自然语言里普遍使用的说法，不是针对某一句的补丁。
  2. **重复**：优先处理多位参与者独立写出的同类说法；只出现一次的记下来，不急着改。
  3. **语义一致**：不破坏原有语义，例如「不想下雨」不能因为含「下雨」就下雨（`src/engine/intent.test.ts` 的否定回归测试必须通过）。
  4. **可追溯**：每次修改在附录「规则校准记录」写明触发样本、改了什么、改前改后的结果（`npm run sentences` 的两份报告）、回归测试结果，以及 10 句固定测试句的命中有没有变化。

  A 组笔迹与句子的系统校准没有单独做（2026-10-29），阈值仍是首轮的值；以后的规则改动都按这四个条件，并记进附录。
- **R1 的「一句成境」只用本地规则，不开 AI，也不设 AI 对照组**（2026-10-25 决定）。实验构建在打包时就固定为本地规则（`sceneMode: local`，带邀请令牌也不会请求 `/api/scene`），而不是靠运行时失败后退回；`world_ready` 记录这一模式，`npm run analyze` 发现测试者之间模式不同、或有句子经 AI 理解时会警告。B 组测试开始后，不根据单个测试者的反馈扩充关键词；规则改动仍按上面四个条件，并按附录记录版本变化。
- 每次发布记录：标签、提交号、改了什么、是否改变所测体验（[附录](#附录发布记录)）。
- 如果某个修复改变了 H1/H2/H3 所测的核心体验，必须标记为新的实验版本，**数据不能直接合并**。
- 每条记录都带着**记录它的那个构建**（构建时写入的提交号、实验编号、日志格式版本），按事件、按回访分别标记，而不是导出时统一打上当前版本：测试期间网站更新过，旧记录仍然标着旧版本，导出文件列出所有版本（`builds`、`mixedBuilds`）。`npm run analyze` 发现版本混杂（包括同一份记录内部混杂）或不是实验构建（开发版、有未提交改动）时会警告。没有版本标记的旧记录标为 `unknown`，不会被算到任何版本头上。
- 送鱼数据和基础 R1 数据分开分析，不混在一起。

## 4. 判定规则（测试开始前写定）

样本很小，百分比不是统计结论。保留明确的 Go / No-Go 机制，同时避免过早否定有潜力的方向。

### 4.1 主持测试（B 组，以 8 名有效测试者计）

| 假设 | 门槛 | 未达标后的行动 |
|---|---|---|
| H1 首次创造（5 秒内无求助落笔） | 8 人中 **≥ 7 人** | 优先排查首屏、触控响应与提示；修复后用新人复测 |
| H2 自主创造（自由段 ≥ 3 次无提示创造） | 8 人中 **≥ 5 人** | **暂停商业功能开发**，研究核心循环和世界深度；**继续**商业价值访谈（是否珍惜已有作品、是否愿意做成实物），以区分问题出在创造过程还是作品价值 |
| H3 主动保存或分享 | 8 人中 **≥ 3 人** | **不启动真实收费实验**，继续调查作品的情感价值；但**允许少量研究性实物打样**，看用户见到实体作品后是否改变看法 |

- 有效人数少于 8 时按原比例（H1 80%、H2 60%、H3 30%）向上取整，报告里会写明「N 人中需 M 人」。
- **无效样本**（中途离开、设备故障、事后发现见过产品等）由观察员在读结果之前写下原因（`notes.json` 的 `invalid` 字段）；它们保留在报告里，但不计入判定。原始日志全部保留。
- 「不确定」：未知（缺观察证据、没有自由段）多到足以改变结论时判为不确定，按 [testkit/测量有效性审查.md](testkit/测量有效性审查.md) 的口径处理，不为凑结论补录。
- H3 只衡量主动保存或询问分享，不是付费意愿指标；它决定的是能否启动**收费**实验，不否定实物方向本身。
- 文字理解不参与 H1–H3 的计算，但文字回应不如预期可能让人不再创造或不想保存。判定规则不变；分析时用观察记录里「文字回应是否成为停手或不想保存的原因」区分画的体验问题和文字回应问题（[主持人手册](testkit/主持人手册.md) §6、[验证报告模板](testkit/验证报告模板.md)）。关键词命中率只是诊断指标，不代表用户感受到的理解质量。

### 4.2 日记式测试（C 组）

| 门槛 | 未达标后的行动 |
|---|---|
| 5 人中 **≥ 2 人**一周内自发回来至少 2 次 | 判断是缺少陪伴价值，还是存在使用场景、设备或入口障碍（比如找不到入口、没加到主屏幕） |

### 4.3 送鱼实验（D 组）

不设单一门槛，记录一条漏斗，分析每个环节在哪里流失：

| 环节 | 记录 |
|---|---|
| 打开 | 收到链接后是否打开（问送鱼人和收鱼人） |
| 收下 | 鱼游到湖边后是否轻触水面收下（`gift_accepted`） |
| 理解 | 访谈：是否明白这是朋友亲手画的鱼 |
| 创造 | 收下后是否画出自己的第一条鱼（`npm run analyze` 的「收到一条鱼之后」） |
| 转送 | 是否主动把自己的鱼再送给别人（`gift_sent`） |

大多数人**没收下**时，先怀疑交互（没看懂「轻触水面」），不要急着判断概念失败。

### 4.4 实物（02 §14）

- H3 达标：允许进入实物需求验证和小批量打样。
- H3 未达标：不启动收费实验；允许少量研究样品。
- 只有在用户表达明确兴趣、供应链成本可接受时，才考虑真实收费实验。

## 5. 测试记录：只在本机，由参与者自己选择导出

- 主持测试：主持人用隐藏面板导出（`?mod`，左上角快速点 5 下），和以前一样。
- 日记式测试、送鱼实验：参与者在自己的手机上使用，记录跨天保存在本机，**由参与者自己决定是否导出**。测试说明里给一个链接（站点地址加 `/?study`），打开后看到：记录了什么、没记录什么、各项计数；可以填写匿名编号（如 P01）后导出，也可以不导出，或删除全部记录。说明文字见 [testkit/送鱼实验说明.md](testkit/送鱼实验说明.md)、[testkit/日记式测试.md](testkit/日记式测试.md)。日记式测试的参与者统一从主屏幕图标使用（先加图标、再从图标画第一笔），图标里没有地址栏，所以「···」菜单里有「测试记录」一项，打开的是同一个页面；浏览器里打开时没有这一项，R1 主持测试看不到它。
- 记录只有时间、次数和事件类型。**没有画的内容、写的字、姓名、手机号或链接。**参与者编号只接受字母、数字和短横线。
- 这一点由存储入口保证，而不是靠每个调用方自觉：每种事件只能保存登记过的字段（`src/lib/study-log.ts` 的 `STUDY_FIELDS`），字符串只能是简短的代号（字母、数字和 `- _ .`），其他字段一律丢弃；读出旧记录时再过滤一遍。新增事件类型不登记就编译不过，新增字段不登记就不会被保存。主持人的内存日志用同一份清单。
- 没有任何自动上传。

## 7. 结果出来后的方向（测试开始前写定）

2026-10-25 决定。和 §4 的门槛一样，下一步的优先级在看到数据之前就写好，不因结果出来时的兴奋或失望临时改变。

**原则：同一时间只有一条工程主线，外加一个不占工程的人工实验。**

候选方向：

| 方向 | 依赖哪项结果 | 工程量 |
|---|---|---|
| A. iOS 日本区首发（02 决策 5） | H1–H3、日记式测试 | 大 |
| B. 实物第二阶段：小规模真实购买（02 §14.2） | H3 | 小，人工收单，不建电商系统 |
| C. 送一条鱼并入正式版 | 送鱼实验漏斗 | 中 |
| D. 世界的深度：远处的鱼轮流游回来、世界种子 | 日记式测试 | 中 |

**主线怎么定：**

| R1（§4.1） | 日记式测试（§4.2） | 主线 |
|---|---|---|
| H1–H3 都达标 | 达标 | **A：iOS 首发**。陪伴型产品的长期价值在手机主屏幕上 |
| H1–H3 都达标 | 不达标 | 先查原因：缺少陪伴价值 → **D**，iOS 推迟；入口障碍（找不到入口、没加到主屏幕等）→ iOS 本身可能就是解法，仍做 **A** |
| H2 或 H3 不达标 | — | 按 §4.1 的行动执行，不进入 A–D |

H1 不达标时，先按 §4.1 修首屏并用新人复测，复测达标后再按上表决定。

**不占工程的人工实验：**
- **B 实物**：H3 达标就开始小规模真实购买，先做「一条鱼的来信」卡片（现有导出已够卡片尺寸，见 [print-readiness.md](print-readiness.md)）；H3 不达标按 §4.4 只做研究样品。

**C 送一条鱼不做主线，只设并入正式版的条件**：D 组 5 人中**至少 3 人收下了鱼**（`gift_accepted`），并且**至少 1 人收下后画出了自己的第一条鱼**。达不到就先改交互（多数人没收下时，先怀疑「轻触水面」没被看懂，见 §4.3），不并入。
